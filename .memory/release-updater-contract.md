# Release and Windows updater contract

- Production YouTube download failures seen on public v2.0.2 were version skew: the cross-platform resolver hardening landed after that release. Current source already contains the resolver fix; no runtime-only production switch was found.
- The direct-release unsigned desktop option must embed `resonanceUpdateAuthenticity=unsigned` in the packaged Windows `package.json`. Production-signed packages embed `production` and continue to require the same valid Authenticode publisher.
- Windows packaging uses an explicit `build.files` allowlist. `main.cjs` began requiring `listening-history.cjs` without that file being added, producing an immediate installed-app startup crash. Keep `validate-packaged-app.cjs` in CI so the built `app.asar` startup dependency closure and embedded updater policy are verified after packaging.
- The packaged Electron executable uses the Windows GUI subsystem even under `ELECTRON_RUN_AS_NODE`, so PowerShell may leave `$LASTEXITCODE` unset after a successful validator run. Invoke it with `Start-Process -Wait -PassThru` and check the returned `ExitCode`.
- The unsigned updater path is valid only when both the installed executable and downloaded NSIS installer report Authenticode `NotSigned`. Environment variables never select a packaged policy.
- Release Studio stages and validates a private draft before publishing. Retries reuse matching assets by name and size, upload only missing assets, and stop on unexpected or ambiguous draft state.
- Release Studio must identify a dispatched workflow by source SHA plus its request ID, not by an exact display-title string; workflow titles may gain fields such as `replace-prerelease`. While monitoring, poll job and step conclusions and surface the first failure immediately with a GitHub-run link and an explicit statement that no release was created.
- Rebuilding an already-tagged version uses the direct workflow's explicit `replace_prerelease` input. That path must resolve the existing GitHub release by tag and require `draft=false` plus `prerelease=true`; the normal path continues to reject every existing tag.
- A candidate build, annotated tag, or private draft is not a public release. Do not claim the YouTube fix is in production until a later explicitly authorized release is published and verified.
- 2026-08-30 live-build audit at `93da774`: all 14 public v2.0.3 assets passed the repository validator; the Windows installer, macOS ZIP, Android APK, and iOS Device IPA matched their published digests, and the three updater manifests matched the corresponding assets. Desktop tests passed 301/301 and release-safety tests passed 27/27.
- The checked-in `publish-release.yml` cannot publish a normal direct candidate whose version/build exceed the `2.0.0 (17)` source floor because it compares the requested release to the baseline policy/version instead of trusted candidate provenance. Its retry verification also compares an annotated tag-object SHA directly to a commit SHA. Keep the direct Release Studio publisher distinct from this recovery workflow until both checks are corrected and tested.
- Public `main` advanced to `3e1ebbeb0b0f35e3f559a9db0e4bacd69ef60f25` during the audit and expanded the public contract from 14 to 18 assets by adding the two iPhone-installer packages and checksums. The audited worktree predates that change and must not be used as the current release head.
- The first signed v2.0.4 direct-release run from that newer `main` failed its macOS and Windows signing-secret validation. Treat production desktop signing as an external release blocker until the environment secrets are restored and a signed canary completes.
- Public v2.0.3 was built by direct-release run `32005595388` with `unsigned_desktop=true`. Its native macOS app embeds `ResonanceUpdateAuthenticity=development` with no Team ID/designated requirement, so the release-mode `UpdateManager` exits before requesting `latest-mac.json`; existing v2.0.3 users cannot self-update and must manually install the next release. Stable direct candidates now reject `unsigned_desktop=true`, production macOS verification checks all three updater policy fields, and the shared Electron Settings UI exposes a manual update check. Do not publish the next stable release until the macOS and Windows signing secrets are restored.
- Developer Mode is a persisted update channel on the shared Windows/macOS Electron app and Android. It selects only non-draft GitHub prereleases carrying the platform's normal manifest (`latest.yml`, `latest-mac.json`, or `latest-android.json`) and never falls back to stable; integrity, identity, and signing checks remain unchanged. iOS has no in-app updater or installable release-discovery channel, so it intentionally has no nonfunctional Developer Mode toggle.
- Developer Mode also overrides ordinary automatic-scan suppression: desktop development/Preview builds scan even when unpackaged (unpackaged source builds report availability but cannot download/install), and Android bypasses its six-hour resume throttle. Concurrency guards and every download/install authenticity gate remain enforced.
- Confirmed Windows data-loss regression: updating a pre-v2 library whose downloaded server songs live directly in `ServerCache` ran `delete-unlinked-downloads-v1` during `library:load`. Pre-v2 server-download records have `remoteID`/`sourceServer` but no preserved source link, so v2.0.0-v2.0.3 called `fs.rm(..., { force: true })`, removed every matching track, and pruned its local playlist/favorite/queue/history references before overwriting `library.json`. This was not an NSIS/userData-path change. The current worktree retires that destructive behavior on Windows, Android, and iOS: it preserves files and every reference, retains accurate server/local provenance flags, and writes the historical migration marker for rollback safety. Realistic legacy and partial-migration regression fixtures cover the compatibility path. Users already affected cannot be reconstructed from the marker alone; server originals can be downloaded again and retained remote playlist/like identities should rehydrate memberships.
 - Repeatable prereleases keep the same human title and base app version but use `vX.Y.Z-pre.<source-commit-unix-seconds>` as their unique GitHub tag. The direct workflow passes that exact tag into macOS and Android manifests; both clients list complete GitHub releases and select the highest valid build. Windows must additionally package the updater-visible semver as `X.Y.Z-pre.<timestamp>` (while retaining base-version installer filenames), because electron-updater will not offer two packages with an equal version. The normal monotonic build/versionCode still advances on every prerelease, and final `X.Y.Z` outranks its prereleases.
 - Existing installed clients cannot discover the prerelease channel until they first receive a stable build containing the release-list resolver. GitHub's `/releases/latest` endpoint excludes prereleases, so do not regress the clients to that shortcut.
